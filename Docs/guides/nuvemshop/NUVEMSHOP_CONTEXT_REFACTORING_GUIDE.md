## PLATFORM CONSTRAINTS (Cannot violate - Nuvemshop requirement)

### CONSTRAINT: Checkout Structure

**Applies To:** `layouts/checkout.tpl`, `static/css/checkout.scss`

**What you CAN do:**
- ✅ Change colors of checkout elements
- ✅ Adjust spacing (padding, margin)
- ✅ Modify fonts and text styling
- ✅ Update button appearance (colors, size)

**What you CANNOT do:**
- ❌ Change form structure or field order
- ❌ Remove form fields (name, email, address, etc)
- ❌ Modify form submission method
- ❌ Hide checkout elements via display:none

**Why:** Nuvemshop's backend handles checkout payment processing. Structural changes break the integration and payment cannot complete.

**If you violated this:**
```bash
# Revert immediately
git checkout -- theme-deploy-corrigido/layouts/checkout.tpl

# Verify
git status

# Commit revert
git commit -m "revert: checkout structure reverted to Nuvemshop defaults"
```

---

### CONSTRAINT: Footer Attribution (Legal Requirement)

**Applies To:** `snipplets/footer/*.tpl`, `static/css/style-critical.tpl`

**What you CAN do:**
- ✅ Style the footer attribution (colors, fonts, spacing)
- ✅ Move it within the footer area
- ✅ Add context around it

**What you CANNOT do:**
- ❌ Hide it with CSS (display:none, opacity:0, visibility:hidden)
- ❌ Hide it via CSS transforms (translate off-screen)
- ❌ Hide it via width:0 or height:0
- ❌ Remove the Nuvemshop store name reference
- ❌ Make it invisible to users

**Why:** Nuvemshop Terms of Service require visible store attribution. This is a legal requirement, not optional.

**If you violated this:**
- Immediately restore footer visibility
- Ensure Nuvemshop store name is visible
- Test in live browser to verify visibility

---

### CONSTRAINT: Form Field Integration (Contact/Registration/Newsletter)

**Applies To:** `snipplets/**/contact*.tpl`, `snipplets/**/register*.tpl`, `snipplets/**/newsletter*.tpl`

**What you CAN do:**
- ✅ Style form inputs (colors, borders, padding)
- ✅ Update placeholder text
- ✅ Add helper text or labels
- ✅ Change button text

**What you CANNOT do:**
- ❌ Modify form field names (name, email, message)
- ❌ Change form submission endpoint
- ❌ Remove required fields
- ❌ Add new backend-required fields

**Why:** Forms sync with Nuvemshop backend (CRM, email, customer data). Field name changes break integration.

## PROJECT GUIDELINES (Can override with justification)

### GUIDELINE: Performance Budget (CSS < 50KB)

**Target:** `static/css/style-critical.tpl` should stay under 50KB

**Why:** Critical CSS is inlined and blocks page rendering. Large files degrade page load performance and Core Web Vitals scores.

**Override Criteria:**
- [ ] Documentation: Why does it need to exceed 50KB?
- [ ] Alternative considered: Can it be split into async CSS?
- [ ] Monitoring plan: How will you track performance impact?
- [ ] Approval: @architect approval required

**If approaching limit (45KB+):**
```bash
# Check file size
wc -c theme-deploy-corrigido/static/css/style-critical.tpl

# Optimize
npm run build:css  # This minifies

# Check if still over
# If yes, consider moving non-critical styles to separate file
```

## DECISION TREE FOR @DEV

```
Making changes to theme files?

1. Is it affecting checkout, footer, or form structure?
   ├─ YES → Check "Platform Constraints" section
   │         If respects constraints → Proceed
   │         If violates → STOP and ask @architect
   └─ NO → Continue

2. Is it affecting CSS file size?
   ├─ YES, approaching 50KB → Check "Project Guidelines"
   │                            If over: Document justification
   │                            Get @architect approval
   └─ NO → Continue

3. Does the change make sense?
   ├─ YES → Implement, test locally, commit
   └─ NO → Ask for clarification before proceeding
```

## DECISION TREE FOR @QA

```
Reviewing changes for FTP deployment?

1. Did developer modify checkout/footer/forms?
   ├─ YES → Use checklist to verify no constraints violated
   │         If violated → REJECT, return to @dev
   │         If compliant → Continue
   └─ NO → Skip to step 2

2. Did CSS file size increase significantly?
   ├─ YES, over 50KB → Is there justification?
   │                    If yes + @architect approved → APPROVE
   │                    If no → Request justification from @dev
   └─ NO → Continue

3. All other checks pass?
   ├─ YES → APPROVE for deployment
   └─ NO → Flag specific issues, return to @dev
```
