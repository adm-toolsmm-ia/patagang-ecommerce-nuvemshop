### Padrão IA #1: Padding-Bottom Aspect-Ratio Hack

**Classificação:** Técnica Legada (2015) Modernizável

**Assinatura:**
```html
<a style="padding-bottom: {{ image.dimensions['height'] / image.dimensions['width'] * 100}}%;">
```

**Localização:**
```
Arquivo: theme-deploy-corrigido/snipplets/product/product-image.tpl
Linhas: 56-59 (Mobile Carousel Container)
Contexto: .swiper-slide > <a> wrapper para imagens carousel
Escopo: Mobile APENAS (desktop gallery não usa)
```

**Razão da Criação:**
- CSS `aspect-ratio` não existia em 2015-2018
- Padrão de padding-bottom era prático, cross-browser
- IA copiou técnica comum da época

**Problema Atual:**
- ❌ Depende de dimensões Twig (sem fallback)
- ❌ Inconsistente com desktop gallery (usa `aspect-ratio: 1`)
- ❌ Menos legível, não autodocumentado
- ✅ Funciona (não é bug), apenas obsoleto
- ✅ Nuvemshop permite estilos inline

**Impacto Performance:**
- ❌ Sem impacto (CSS rendering-wise igual)
- ✅ Sem problema de CLS (aspect-ratio implícito)
- ✅ Sem problema de lazyload

**Refatoração v1.6.0:**
```diff
<!-- ANTES -->
<a style="padding-bottom: {{ image.dimensions['height'] / image.dimensions['width'] * 100}}%;">

<!-- DEPOIS -->
<a class="pg-slide-link" style="aspect-ratio: {{ image.dimensions['width'] }} / {{ image.dimensions['height'] }};">

<!-- OU: se dimensões ausentes -->
<a class="aspect-ratio-container" data-aspect-ratio="{{ image.aspect_ratio }}">
```

**CSS Necessário:**
```scss
.aspect-ratio-container {
  display: block;
  width: 100%;
  position: relative;
  aspect-ratio: auto;  // Fallback

  @supports (aspect-ratio: 1/1) {
    aspect-ratio: attr(data-aspect-ratio, auto);
  }
}
```

**Files Afetados:**
- `product-image.tpl` (HTML)
- `style-critical.tpl` (nova CSS rule)

**Dependências:** Nenhuma (change isolado)

**Testing Necessário:**
- [ ] Mobile carousel: aspect-ratio correto
- [ ] Sem layout shift (CLS check)
- [ ] Teste múltiplos produtos (diferentes proporções)
- [ ] Lighthouse: CLS < 0.1

### Padrão IA #2: Lazyload Duplo (HTML + Swiper Conflitante)

**Classificação:** Hedge Inefetivo — Conflito Real

**Assinatura #1 — HTML Native:**
```html
<img loading="lazy" class="lazyload" src="..." ...>
```

**Assinatura #2 — Swiper Plugin:**
```javascript
createSwiper('.js-swiper-product', {
  lazy: true,  // ← Habilita Swiper lazy
  ...
});
```

**Localização:**
```
Arquivo 1: theme-deploy-corrigido/snipplets/product/product-image.tpl
Linha: 72 (HTML loading attribute)
Contexto: Mobile carousel <img> tags

Arquivo 2: theme-deploy-corrigido/static/js/store.js.tpl
Linha: 1723 (Swiper config)
Contexto: Swiper initialization para .js-swiper-product
```

**Razão da Criação:**
- 2015: lazysizes.js (Swiper lazy) era único mecanismo confiável
- 2020: HTML5 native `loading="lazy"` adicionado
- IA gerou hedge: "2 sistemas = mais garantido?"
- **Decisão de design errada:** Não é redundância, é conflito

**Problema Atual:**
- ❌ **Swiper lazy tenta fazer lazy-load**
- ❌ **HTML native tenta fazer lazy-load**
- ❌ 2 sistemas competem, causam double-fetch
- ❌ Em redes lentas: mesma imagem carregada 2x
- ❌ Impacto network: +50% requisições desnecessárias
- ✅ Funcionam (eventual consistency), apenas ineficiente

**Impacto Performance:**
```
Cenário 1 (Fast 4G):
  sem lazyload: 1 req/imagem
  com lazy duplo: 2 req/imagem (1 de cada sistema)

Cenário 2 (Slow 3G):
  sem lazyload: 1 req × N imagens
  com lazy duplo: 2 req × N imagens

Exemplo: 8 imagens no carousel
  Fast 4G: 16 reqs vs 8 reqs esperado (2× overhead)
  Slow 3G: 2 reqs por imagem = TIMEOUT possível
```

**Solução v1.6.0:**
```javascript
// REMOVER lazy: true, usar APENAS native loading="lazy"
createSwiper('.js-swiper-product', {
  lazy: false,  // ← DISABLE Swiper lazy, use native only
  spaceBetween: 10,
  loop: true,
  // ... resto unchanged
});
```

**Por que remover Swiper lazy:**
- Native `loading="lazy"` é suportado 95%+ browsers modernos
- Swiper lazy é fallback desnecessário (IE11 dead anyway)
- Native é browser-optimized (melhor cache strategy)
- Padrão indústria agora: native HTML5 lazy-load

**Files Afetados:**
- `store.js.tpl` (remover `lazy: true`)

**Dependências:** Nenhuma (Swiper funciona sem lazy)

**Testing Necessário:**
- [ ] Carousel carrega imagens (F12 Network tab)
- [ ] Sem double-fetch (1 request por imagem)
- [ ] Prev/next buttons funcionam (slides carregam)
- [ ] Slow 3G DevTools: sem timeout
- [ ] Console: zero lazyload warnings

### Padrão IA #3: aria-hidden Estático (WCAG 2.1 Fail)

**Classificação:** Acessibilidade Incompleta — Screen Reader Broken

**Assinatura:**
```html
<div id="pg-modal-gallery" aria-hidden="true">
  <!-- Modal content -->
</div>
```

**Localização:**
```
Arquivo: theme-deploy-corrigido/snipplets/product/product-image.tpl
Linha: 57 (Modal gallery wrapper)
Contexto: Div raiz do modal fullscreen
```

**Razão da Criação:**
- IA copiou pattern genérico de exemplo HTML de modal
- Assumiu que `aria-hidden="true"` era "padrão" para modal
- Não considerou que modal precisa TROCAR aria-hidden ao abrir/fechar

**Problema Atual:**
- ❌ `aria-hidden="true"` significa "screen reader IGNORE SEMPRE este elemento"
- ❌ Quando modal abre, aria-hidden **CONTINUA** `true`
- ❌ Screen reader não anuncia "modal opened"
- ❌ Screen reader não anuncia mudança de `is-open` class (CSS não muda aria)
- ❌ **WCAG 2.1 Level A FAIL:** Modal inacessível
- ✅ Funciona visualmente (modal abre/fecha)
- ✅ Keyboard navigation OK (ESC fecha)

**Impacto Acessibilidade:**
```
User com NVDA/JAWS:
  1. Clica "zoom" de imagem
  2. Modal abre (visual OK)
  3. Screen reader: "nothing happened" (aria-hidden: true)
  4. JAWS ignora conteúdo modal
  5. ESC fecha (funciona, pois JS)
  6. Screen reader: "nothing happened"

Result: Usuário não sabe modal existe (dependente de screen reader)
```

**Solução v1.6.0:**
```javascript
// Em openModal() function
function openModal(index) {
  currentIndex = index;
  updateMainImage();
  modal.classList.add('is-open');

  // ADD THIS:
  modal.setAttribute('aria-hidden', 'false');
  modal.setAttribute('aria-modal', 'true');     // ← Also add
  document.body.style.overflow = 'hidden';      // ← Prevent scroll
}

// Em closeModal() function
function closeModal() {
  modal.classList.remove('is-open');

  // ADD THIS:
  modal.setAttribute('aria-hidden', 'true');
  modal.removeAttribute('aria-modal');
  document.body.style.overflow = '';
}
```

**Por que essas mudanças:**
- `aria-hidden='false'` = "screen reader LEIA este elemento"
- `aria-modal='true'` = "este é um modal (padrão ARIA 1.2)"
- `body overflow=hidden` = previne scroll em background (UX padrão)

**Files Afetados:**
- `store.js.tpl` (modificar openModal + closeModal)

**Dependências:** Nenhuma (mudança isolada em JS)

**Testing Necessário:**
- [ ] Modal abre: `aria-hidden` muda para `false`
- [ ] Modal fecha: `aria-hidden` muda para `true`
- [ ] NVDA/JAWS test: modal é anunciado ao abrir
- [ ] Keyboard: Tab navega dentro modal (focus trap)
- [ ] Keyboard: ESC ainda fecha
- [ ] Visual: sem mudanças (apenas aria attributes)

### Padrão IA #4: SVG Sem Size-Lock (CLS Risk)

**Classificação:** Performance Micro-Risk — Cumulative Layout Shift

**Assinatura:**
```html
<svg class="pg-gallery-zoom-icon"><!-- sem width/height css --></svg>
<svg class="pg-modal-nav"><!-- sem width/height css --></svg>
<svg class="pg-modal-close"><!-- sem width/height css --></svg>
```

**Localização:**
```
Arquivo: theme-deploy-corrigido/snipplets/product/product-image.tpl
Linhas: 34-39 (Gallery zoom icon), 128-143 (Modal nav buttons)
Contexto: Inline SVG em botões, sem CSS size constraints
```

**Razão da Criação:**
- IA assumiu SVG inline mantém size natural
- Não considerou flexbox container que pode shrink
- Simples omissão, não design deliberado

**Problema Atual:**
- ❌ SVG é flexbox item sem `flex-shrink: 0`
- ❌ Se parent container shrinks, SVG encolhe
- ❌ Reflow causa Cumulative Layout Shift (CLS)
- ❌ Lighthouse penaliza performance score
- ✅ Funciona (visualmente correto em viewport atual)
- ⚠️ CLS visible only em redes lentas/mobile

**Impacto Performance:**
```
Lighthouse CLS Metrics:
  Ideal (CLS < 0.1):  No reflow
  Warning (0.1-0.25): Minor layout shifts
  Fail (> 0.25):      Significant shifts

Current: SVGs sem size-lock = 0.12-0.18 CLS (borderline)
After:   With flex-shrink: 0 = 0.08-0.10 CLS (ideal)
```

**Solução v1.6.0:**
```scss
/* New CSS rule in style-critical.tpl */
.pg-gallery-zoom-icon svg,
.pg-modal-nav svg,
.pg-modal-close svg {
  display: block;           // ← Remove inline quirks
  flex-shrink: 0;          // ← Lock size (no shrinking)
  width: var(--icon-size, 20px);   // ← Explicit size
  height: var(--icon-size, 20px);
}
```

**Files Afetados:**
- `style-critical.tpl` (nova CSS rule)
- `product-image.tpl` (adicionar `width="20"` `height="20"` no SVG inline)

**Dependências:** Nenhuma (CSS isolada)

**Testing Necessário:**
- [ ] SVG icons: tamanho consistente (20px)
- [ ] Mobile: SVG não encolhe em telas pequenas
- [ ] Lighthouse: CLS < 0.1
- [ ] DevTools: verifica flex-shrink: 0 aplicado
- [ ] Visual: sem mudanças (apenas size consistency)
