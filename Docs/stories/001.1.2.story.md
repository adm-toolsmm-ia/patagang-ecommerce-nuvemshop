### 3. User Story (Clear Intent)

```
As a developer,
I want a documented and tested CSS caching workaround,
So that CSS changes are immediately visible after deployment
without waiting for browser cache expiration.

ACCEPTANCE CONTEXT:
- Current State: CSS changes cached for 30+ days (Nuvemshop FTP default)
- Target State: CSS change visible within 2 seconds of FTP deploy
- Blocker: Must be solved before implementing CSS changes (Stories 1.3+)
- Platform: Nuvemshop FTP model requires manual cache busting
- Solution: Query parameter versioning (?v=YYYY-MM-DD-NNN)
```

### 4. Acceptance Criteria (Testable Checklist)

**AC-1: Cache Busting Mechanism Implementation**
```
□ CSS cache-buster query parameter added to theme layout (?v=)
□ Version format: YYYY-MM-DD-NNN (date + sequential number)
□ Version parameter applied to ALL CSS links in theme
□ Build script auto-increments version on CSS file changes
□ Example: href="/css/style.css?v=2026-03-24-001"
□ Version stored in build metadata file for tracking
```

**AC-2: Deploy Script Integration**
```
□ FTP deploy script updated with version bumping logic
□ Script detects CSS file changes (file hash comparison)

□ No manual version management required
□ Deploy script documented for team
```

### 10. Rollback Plan (< 5 min recovery)

**Rollback Decision Criteria:**
```
Rollback if:
□ Cache busting not working (CSS not updating)
□ Version parameter breaking CSS load
□ Build script failing on production
□ Team cannot deploy using new procedure

Default: Very safe change (low rollback probability)
Probability of rollback: < 5%
```

**Rollback Procedure (< 5 minutes):**

```
STEP 1: Identify Problem (< 1 minute)
  □ CSS changes not visible after deploy
  □ Or: Build script failing
  □ Verify issue in 2+ browsers
  □ Document the specific issue

STEP 2: Stop the Bleeding (< 2 minutes)
  □ FTP into production (theme area)
  □ Locate: theme/layouts/layout.tpl (or index file)
  □ Remove ?v=YYYY-MM-DD-NNN from CSS links
  □ Revert to plain: href="/css/style.css" (no version)
  □ FTP upload changes
  □ Clear theme cache if possible

STEP 3: Verify Rollback (< 1 minute)
  □ Refresh production homepage
  □ Confirm: CSS loads without version param
  □ Confirm: No console errors
  □ Verify in 2+ browsers

STEP 4: Post-Mortem (after verification)
  □ Create incident ticket
  □ Document what went wrong
  □ Determine root cause
  □ Plan fix for next attempt
  □ Update build script
  □ Re-test in staging
  □ Re-deploy after fix
```

**Rollback Files:**
```
Primary: Build script (remove version bump logic)
├─ Action: Revert to previous version (git revert)
└─ Impact: Version param stops incrementing

Secondary: Deploy script (remove version param)
├─ Action: Remove ?v= from CSS links
└─ Impact: CSS links revert to plain URLs

Timing: < 5 minutes total
Validation: 2-browser test on production
```

**Escalation Matrix:**
```
If rollback needed:
  1. Notify: Engineering Manager + QA Lead (immediately)
  2. Assess: Is checkout broken? (primary concern)
  3. Execute: Rollback (< 2 min)
  4. Validate: 2-browser test on production
  5. Communicate: Update team in Slack
  6. Investigate: Root cause analysis
  7. Fix: Address issue in new branch
  8. Re-test: Staging validation
  9. Re-deploy: When fixed and approved
```
